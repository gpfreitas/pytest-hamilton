# Initial Design

## The Basic Idea – Without a pytest plugin

The idea is to have automatic fixtures generated by hamilton. For example, in another project, I have a python module
with the following data processing functions:

```python
# lib_model.py

import pandas as pd
from contextlib import closing
import queries  # this is a module I also coded myself

def columns(features: list, label: str) -> list:
    return [*features, label]

def data(columns: list = queries.DEFAULT_COLUMNS) -> pd.DataFrame:
    """Get dataframe with columns that were asked for."""
    with closing(sqlite3.connect("../data.db")) as conn:
        query = queries.boston_house_prices_query(columns=columns)
        df = pd.read_sql_query(query, conn)

    return df

def data_notnull(data: pd.DataFrame) -> pd.DataFrame:
    """Drop nulls."""
    data_notna = data.dropna(how='any')

    # this is logging useful stuff, not part of the pipeline
    if (n_post := data_notna.shape[0]) < (n_pre := data.shape[0]):
        logger.info("Dropped {n_post - n_pre} rows due to NULL values")
        top_null_cols = data.isna().sum().value_counts().sort_values().tail(3).to_dict()
        logger.info("3 Columns with the most NULLs: {top_null_cols}")

    return data_notna
```

I want to be able to pass in the input variables to pytest via a config file, for example:

```json
{
    "db": "data.db",
    "table": "boston_house_prices",
    "features": ["chas", "nox", "rm", "dis", "ptratio", "b", "lstat"],
    "label": "medv"
}
```

and then be able to write _and run_ the following tests:

```python
# test_lib_model.py

def test_data(data):
    """Test data we pull.
    """
    assert data.shape[0] > 0
    assert data.shape[1] > 0


def test_data_notnull(data_notnull):
    """Test the dataframe we pull after dropping NULLs.

    We could write many more tests here. Anything you expect to be true of the data at all times can go in the test.
    """
    # GIVEN test data
    # THEN the label 'medv' must be present and its values non-null
    assert data_notnull["medv"].notna().all()
    # and positive
    assert (data_notnull["medv"] > 0).all()
```

To support that, I wrote something like this in my `conftest.py`. Basically this file imports a hamilton driver
(`hamilton_fixture_driver`) and loops over the variables (hamilton DAG nodes) defined in the driver to create pytest
fixtures on the fly (it delegates the actual computation to `hamilton_fixture_driver`).

That's what makes it possible to write tests that run with fixtures that we don't have to code ourselves.


```python
# conftest.py

"""Pytest config and central place for fixtures.

This is a file for pytest-sake only.

https://docs.pytest.org/en/stable/reference/fixtures.html#conftest-py-sharing-fixtures-across-multiple-files

Examples of things we do here:

- Import fixtures that we will use in tests.

"""

import logging
import sys
from pathlib import Path

import pytest
from fixtures import (  # noqa
    hamilton_fixture_driver,
    hamilton_fixtures,
    input_config,
)

logger = logging.getLogger(__name__)


FIXTURE_CACHE = Path(".hamilton_cache")

### Fixtures

# In order to keep conftest.py a bit cleaner and more about configuration, fixtures should be defined in the fixtures.py
# module and imported here.

# In particular, we have a Hamilton-backed fixture defined there that returns a dictionary with all the output of the
# Hamilton DAG that are requested by a test. Here, we unpack that dictionary and set the corresponding nodes one by one
# as standalone fixtures (so we have fixtures named after the names of each of the output nodes in the Hamilton DAG).

this_module = sys.modules[__name__]
for node in hamilton_fixture_driver.list_available_variables():
    # In this loop we defined pytest fixtures using hamilton to do so automatically.
    #
    # We need the fixture_wrapper function to avoid late binding problems.
    # See: https://stackoverflow.com/questions/3431676/creating-functions-or-lambdas-in-a-loop-or-comprehension
    # Late binding would lead all fixtures to be the same, as determined by the last iteration
    # Using the wrapper we ensure each hamilton_backed_fixture function has its own closure and that the correct
    # node.name is stored in each closure.
    def fixture_wrapper(varname=node.name):
        @pytest.fixture
        def hamilton_backed_fixture(hamilton_fixtures):  # noqa: F811
            return hamilton_fixtures.get(varname)

        return hamilton_backed_fixture

    setattr(this_module, node.name, fixture_wrapper(node.name))
```

Finally, we have the `fixtures.py` that creates the `hamilton_fixture_driver`:

```
# fixtures.py

import pytest
import hamilton.driver
import logging
import lib_model


logger = logging.getLogger(__name__)


### Fixtures built automatically from the Hamilton DAG.

# For the Hamilton-backed fixtures, we will need a Hamilton driver. Include all modules that have hamilton functions
# (DAG node definitions) in the .with_modules() call.
hamilton_fixture_driver = (
    hamilton.driver.Builder()
    .with_config(dict())  # is this needed?
    .with_modules(lib_model)
    .with_cache()
    .build()
)


# Note: It would be nice if this fixture was scoped to "session" and we could collect all the request fixtures for the
# whole test suite... but if we do that, we will have only the request fixtures of the first test. As far as I know,
# there is no way to collect all the request fixtures in the whole pytest run and reference them here (see
# requested_features in the body of the function). So we go with function/test scope (default) and let the request
# fixture handle that then for us. This means we rebuild the necessary fixtures for each test. That may seem
# inefficient, but with disk-based caching, it turns out not to be the case (we do have to read the file from cache
# again every time, but it's not a big deal). Again, the ideal would be to build the fixtures once for the session, but
# there is no clear path for that.
@pytest.fixture
def hamilton_fixtures(
    request,
    input_config: dict,,
):
    """Returns a dict of hamilton DAG fixtures.

    Args:
        request (type[FixtureRequest]): built in pytest request fixture.
        input_config (dict): fixture defined by --flow-config pytest cli option.

    Returns:
        dict: return object from driver.execute(); mapping of hamilton DAG node_names to node_values

    """
    # Below we rely on a global variable `hamilton_fixture_driver` which is not nice but... it works for now. I want
    # that driver to be available for interactive use too, so I don't want to make it into a fixture. Mabe we could have
    # both.

    # Step 1: determines which hamilton DAG nodes need to be computed
    hamilton_vars = set(node.name for node in hamilton_fixture_driver.list_available_variables())
    requested_fixtures = set(request.fixturenames)
    hamilton_fixtures = hamilton_vars.intersection(requested_fixtures)

    # Step 2: compute the requested fixtures
    logger.info("Loading hamilton_fixtures...")
    inputs = {"input_config": input_config}  # first the inputs
    fixtures = hamilton_fixture_driver.execute(final_vars=hamilton_fixtures, inputs=inputs)
    # fixtures is a dictionary. Note that above we used again that global `hamilton_fixture_driver` assumed to exist.

    logger.debug(f"Non-NULL hamilton fixtures: {[k for k in fixtures if fixtures[k] is not None]}")
    logger.debug(fixtures)
    logger.info("[DONE] Loading hamilton_fixtures.")

    return fixtures


### 3. Other fixtures (Optional) - Custom, Hand-crafted Fixtures Not Encoded in the Hamilton DAG

```

## The Challenge – Turn the Idea Above Into a Plugin

I want to make the code above, say, in `lib_model.py`, `test_lib_model.py` work with a simple import of
`pytest-hamilton`. The plugin should create the following objects (or equivalent functionality):

- `hamilton_fixture_driver` and `hamilton_fixutres` from `fixtures.py` above.
- `fixture_wrapper` from `conftest.py` above.

It should also create CLI arguments for pytest so that we can pass in the `input_config` (a path to a JSON file, say) as
a cli argument to pytest.
